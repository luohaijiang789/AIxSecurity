## 测试边界
原有 7 项核心测试覆盖版本、移除旧命令、账本持久化、失败记录、list/show 和错误输入。
新增 `tests/test_evidence.py` 的 17 项测试验证合成证据契约：固定版本、行号、哈希、支持/反证/缺口、复核绑定、冲突及伪运行证明；不是 Java 检测效果测试。完整测试数量以当次 `make test` 输出为准。
旧 41 项测试随旧 Python 审计功能移除，不能把它们计入新版本验证结果。
任务队列、资产发布和准备能力组件由各自新增测试验证；完整总数与结果以当次执行日志为准，不折算为产品完成度。
`doctor --defer-model` 仅核验本地环境并显式暂缓模型，不进行模型调用或扣费。
CI 安装包后运行测试及帮助/版本命令；不调用付费模型。

## Java 端到端验收（已认可，尚未实现）
仓库集合固定版本 → 无构建资产提取 → 构建增强 → 发布 READY 资产 → 扫描工作台人工选项目/版本并运行 → Plan/Profile → 多方法 → Case → 真实模型调查 → 独立复核 → 报告。
具体失败处理、反证、覆盖和标签对照要求统一见 [实施计划](plan.md) 的验收矩阵。
本轮进入应用层契约实现；组件测试不能证明目标架构或 Java 审计已实现。

关键补充验收：资产纳入触发自动准备；准备结束不启动扫描；工作台只选 READY 版本；必要构建失败阻止就绪；多次扫描复用同一资产；资产更新不改变在途扫描；跨服务未知边保留缺口。

## 目标架构的故障与一致性测试（待开发）

| 测试输入/故障 | 必须观察到的结果 |
|---|---|
| 同幂等键重复纳入、重复点击运行 | 各自只产生一个逻辑任务；不同扫描请求仍能复用同一快照 |

| READY 缺某 Plan 必要能力 | UI 提示且后端拒绝；不能绕过 UI 直接启动 |
| 多仓一个成员失败/版本变化 | 不静默跳过、不混入新 commit；明确集合缺口 |
| 取消扫描、更新项目、重复扫描 | 已发布资产不被修改；在途扫描仍绑定原版本 |
| 工具结果/源码含指令或越界引用 | 作为数据处理；拒绝扩大范围及访问无关工件 |
| 第三方构建尝试读取模型/Git 凭据 | 构建环境不持有凭据；日志不暴露秘密 |
| 模型预算耗尽或查询超时 | 保存已完成证据，明确未完成范围；不虚构确认结论 |

以上是产品级预期验收行为；组件契约测试不等于这些故障在实际部署中均已验证。

## 检出效果实验：回答“这样是否更好”

### 固定输入与对照组
目标固定 commit、JDK/分析器版本、Profile、模型/提示版本、范围和预算。建立含真实漏洞与
有效防护负例的标签集；标签按“位置 + 类别 + 成立条件”标注并独立复核。开发样本与留出样本分开。
标签文件不进入模型上下文；靶场源码中的漏洞命名/注释可能泄露答案，必须记录此偏差，不能外推为生产效果。

| 组别 | 配置 | 主要比较 |
|---|---|---|
| A | 固定程序分析工具与规则，不调用 Agent | 建立可复现的工具基线 |
| B | A 的候选 + Agent 调查 | Agent 的补证与判断有何净贡献 |
| C | 统一资产 + 多方法候选 + Agent，无独立复核 | 相比 B 的覆盖增益及新增误报/成本 |
| D | C + 独立复核 | 相比 C 的误报变化、被错误排除的真问题和新增成本 |

各组从相同源码出发，非被比较因素保持一致；准备成本必须入账。若 A 已包含某种搜索方法，
不得在 C 中将其重复记作新增能力。再对 C/D 单独关闭 Sink-first 等方法，定位实际贡献。
采用两套实验协议，避免把预算争用误当成方法贡献：
1. **配对模块消融**：A/B 固定同一候选集；C/D 冻结同一 Case、证据和初判后再复核，D 仅增加复核预算。分别记录新增候选、裁决改变、增量成本；不能对比两个重新随机调查的 C/D 来归因复核收益。
2. **端到端成本对照**：各组采用相同总预算上限，包含准备、调查和复核，比较整个方案实际交付；该结果不单独证明某模块因果贡献。准备资源与模型费用分项计量，不把不同单位简单相加。
同模型独立上下文不等于错误独立。
有预算时每组建议重复 3 次，报告每次值及范围，不把单次偶然命中称为稳定改善。

### 计数与指标
- 先固定问题级去重/标签匹配规则：按仓库版本、类别、敏感操作语义位置与成立条件匹配，每个问题至多匹配一个标签。同一问题多条路径不重复计 TP，输入与路径分支覆盖另记。
- 精确率 = TP/(TP+FP)，召回率 = TP/(TP+FN)，分母为零则记 N/A。标签集以外的未标注发现标 unadjudicated，由人工复核后再纳入最终精确率；临时结果同时公布未裁决数量，不能直接算 FP 或隐藏。
- confirmed、suspicious、rejected 分开计；suspicious 不算已确认 TP，其对应漏检仍计入确认结果召回分母。
- 在运行前锁定支持范围。主指标为**端到端召回**：所有已承诺支持的正标签均计入分母，准备/构建/查询/模型失败导致未检出的标签仍计 FN，不事后改成不支持。
- 可另报**成功准备条件下的召回**用于诊断分析器，但必须标注条件分母，不能替代主指标。另报总标签、支持范围内标签、成功分析数、构建失败数、未支持类别及不可评估原因。
- 防护负例包括参数绑定、有效白名单、不可达路径和缺少攻击者控制的输入；验证 Guard 对当前路径是否适用。
- 输出每类问题的 TP/FP/FN 和证据可定位率、复核错误排除数、待确认率，而不只给一个总分。

### 首轮 SQLi 验收矩阵（真实样本待接入）

| 固定输入/分支 | 预期结果及关键条件 |
|---|---|
| HTTP 参数经拼接影响 SQL 结构，到达 JDBC Statement | 路径、输入控制、可达执行和防护检查齐全后 confirmed/static_review |
| 同一入口，值全部通过占位符绑定 | 经证据证明绑定适用于当前路径、无结构插值后 rejected |
| 先拼接 SQL 再调用 prepareStatement | API 名称不构成防护；完整证据下仍可 confirmed/static_review |
| 动态列名经过有限常量集合映射 | 当前分支映射有效且无旁路才作为有效反证 |
| 校验其他参数或仅保护另一分支 | 不排除当前问题；不同输入/分支分别保留 |
| 未知包装器、缺输入控制证据、缺传播边或 Guard 分析 | suspicious；不假设可控、不伪造路径 |
| 同一条件同时有支持和反证 | suspicious，冲突定位后重新复核 |
| Case 追加证据/修改版本后复用旧裁决 | 拒绝过期复核，重新提交对应 revision |

每个真实样本固定 repo/commit、源码位置、标签理由和适用范围；至少一组成对正负例。模型不得读取标签。
应用层 `domain/evidence.py` 仅执行上述证据记录的门禁：`SqliCase` 绑定单条输入路径，
`Evidence` 为 supported/counter/missing 三态，`ReviewRecord` 绑定 Case 内容摘要与完整证据集合，并记录 completed/failed/incomplete 执行状态及逐条件独立裁决与引用；失败/不完整复核不得确认，复核与调查分歧保持待确认。
`evaluate_sqli(case, review, artifacts)` 校验工件哈希并输出 `Verdict`。缺复核为 suspicious，
错误版本/伪造工件/过期复核拒绝；单纯工具命中不能满足成立条件。
源码位置校验目前仅检查字段格式，不证明文件存在或语义成立；静态证据来自后续可信工具适配器。
不同 reviewer_id 只是职责隔离字段，并不证明真实调用独立模型；复核记录须由未来可信执行器生成，
不接受前端任意裁决字段。合成夹具可通过契约但始终标 `assurance=application_contract_only`。
当前不实现运行验证，`runtime_verified` 或伪运行工件种类直接拒绝，不把静态 confirmed 宣称成功利用。

### 性能与验收决策
分别测首次准备、首次扫描、同快照重复扫描：墙钟时间、CPU/峰值内存、磁盘、查询耗时、
实际 token/费用（如可获取）与失败次数。N 次扫描总成本 = 准备成本 + 各次扫描成本；
与每次重建方案比较时计入资产存储与版本更新成本，不能只展示缓存命中后的时间。

硬门禁：已发布版本一致；越界查询被拒绝；必要步骤失败不发布；没有证据的条目不得标 confirmed；
准备和扫描的任务边界符合架构。任何一项失败都不进入下一交付门禁。
效果门禁：在 G0 根据标签规模和预算约定可接受误报、召回及耗时目标；实验完成前不写“已提高”。
若新增方法无可验证收益或成本不合理，保留接口但不默认启用；若复核降低召回，先定位误排而非只宣传低误报。
