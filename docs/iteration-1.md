# 第一轮：可追踪、可复现的审计基础

## 已落地
- Config → application → Analyzer → deterministic report，CLI 另行写入 SQLite RunLedger。
- schema v2 增加生效配置、coverage 和 finding fingerprint；保留原有 manifest/findings/skipped。
- 指纹输入：规则 ID、相对路径、行号、源文件 SHA256、证据类型。适合同一快照去重；源文件任何变化都会改变指纹，不宣称跨版本语义匹配。
- 运行信封保存 ID、时间、目标路径、配置、状态、完整报告或错误。开始/结束分别提交事务；报告原子落盘。
- 运行状态：running → completed / partial / no_supported_files / failed。Ctrl-C 记 failed，CLI 返回 130。
- unsupported_files 与 excluded_directories 独立记录。被排除目录只记录边界，不递归统计其中内容；不是全仓库覆盖率百分比。
- 文件数、单文件读取量、总读取量限制生效，预算触发后停止遍历并标记 partial。读取最多用 1 字节探测超限。

## 仍需解决的架构问题
1. **账本不是恢复引擎**：强杀可能留下 running；暂无 checkpoint/resume。下一步按阶段/文件记录幂等键（快照、配置、分析器版本），恢复时重新验证，不盲目重用旧结果。
2. **源快照尚未固化**：当前 manifest 仅包含成功解析文件的哈希；输入要求稳定快照，不支持恶意并发路径替换。下一步先独立采集内容寻址快照，再从快照分析，并记录失败文件哈希。
3. **资源隔离尚未完成**：当前限制读取预算，不是目录枚举/AST CPU/内存/墙钟上限；下一步把 Analyzer 放入独立 worker 进程并添加超时和终止回收。
4. **双写不具备跨资源原子性**：JSON 写入后数据库提交失败可能留下报告；下一步用产物哈希/状态机协调，并可从账本重新导出报告。
5. **契约仍需细化**：Finding 已有指纹，但 Evidence/AnalysisResult/Review 仍需版本化类型；模型必须引用真实 evidence ID，不直接产生 confirmed。

## 下一批优先级与验收
- P0：快照采集 + worker 隔离；任何样本超时不能阻塞后续文件，源文件不执行。
- P0：阶段检查点 + runs resume；重启后不重复已验证阶段，输入变化拒绝复用。
- P1：分析器结果类型 + CodeQL 报告导入；分清语法、数据流和动态证据，保留原始工具版本。
- P1：基准样本集 + 精确率/召回率；先锁定语言、规则类别、样本划分，再讨论效果。
- P2：有预算的模型复核；模型配置/提示版本可追踪，不将仓库内容视为执行指令。
