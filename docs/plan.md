## 2. 已认可的首轮切片与待核验选型
- 输入和资产模型支持一个或多个 Java 微服务仓库；首个验收样本建议先选单仓 Maven/Spring MVC。
- 之后用两个服务验证集合版本、服务映射与关联缺口；不把跨仓资产可查询等同跨服务漏洞已可证明。
- 一个用户显式选择的专项深扫 Plan，通过 Profile 参数组合方法，不只写一个线性脚本。
- 首类建议 SQL 注入：同时验证 Source-first、Sink-first、规则、路径证据、有效参数绑定反例。
- 跑通后增加路径遍历、命令注入等靶场实际支持的类别，验证架构复用而非复制 Agent。
- RPC/MQ、二阶输入、跨仓等保留模型与 unknown 状态，首版不宣称完成分析。
- 工具具体版本、框架精度、图存储与模型用量尚未核实，不提前承诺性能与召回率。

## 3. 分阶段开发顺序

| 阶段 | 交付 | 完成门槛 |
|---|---|---|
| D-01 环境与样本核验 | 单仓/多仓输入清单、固定 commit、构建要求、Sourcebot/CodeQL 适配可行性；模型连通按用户要求暂缓 | 目标可获取，配置可用；记录真实阻塞，不输出密钥 |
| D-02 资产管理界面与接入 | 项目/仓库纳入表单、列表/详情、仓库集合接入清单、后台任务触发；Pass 1 提取器 | 保存纳入后自动持久化排队；幂等提交不重复建任务；状态/错误可见；Entry 与 Source 分离；不是只有 CLI |
| D-03 构建增强与资产就绪 | 隔离构建、搜索索引/程序库、增强资产、AssetSnapshot/RepositorySetSnapshot、ReadinessReport | 必要步骤与质量门禁通过才发布；能力/质量清单绑定版本；重试和中断恢复不重复发布；失败保留 Pass 1 和旧版本；就绪不启动扫描 |
| D-04 扫描工作台与查询契约 | READY 项目/版本选择、模式/Profile/预算表单、运行按钮、ScanRun、Query Service | 点击运行才创建扫描；未就绪不可选；前后端同时验证能力/质量；所有查询绑定 commit；重复点击幂等，取消不删资产 |
| D-05 多方法与 Case | Source-first 主链、Sink-first 补漏、规则触发、路径查询、Case 合并 | 同一问题多触发可关联；不同路径不丢失；同源证据不重复算佐证 |
| D-06 Agent Investigation | 编排器分配 Case/服务任务，真实模型接入、受控补证、轨迹 | 至少一次真实补证调用；引用可校验；越界请求被拒绝；停止条件留理由 |
| D-07 Verification / Report | 独立上下文复核、Verdict、JSON/Markdown | 支持/反证/缺证分开；静态复核不写成动态利用；报告含缺失能力 |
| D-08 靶场对照与工程交付 | 增加 Profile、标签对照、安装测试、用户文档、提交与 CI | 真实 Java+模型链与 mock 分开；执行 testing.md 的对照实验；给出误报/漏报/不可评估范围及冷/热成本 |

### 3.1 按可演示闭环设门禁，而不是一次开发全部模块
- **G0：契约与选型通过（D-01）。** 固定目标版本，验证 Java 建库模式、查询覆盖与执行隔离；模型连通主动暂缓并移交 G3 入口，不因此阻塞离线资产阶段；记录资源需求。Sourcebot 若不满足固定版本取证，先用可替换的轻量检索适配，不阻塞核心闭环。
- **G1：自动准备可用（D-02～03）。** 用户在真实界面纳入仓库，不手工执行后台脚本；看到 READY 资产及接口/安全对象；演示构建失败、重试、进程重启和旧快照保留。暂时没有调查 Agent 也可以验收此阶段。
- **G2：人选扫描可用（D-04～05）。** 工作台选 READY 版本与专项计划，生成真实程序证据和统一 Case；能力不足被拒绝，准备完成不会自动扫描。
- **G3：调查—复核—报告闭环（D-06～07）。** 真实 Agent 至少完成一次受控补证，独立复核处理正例/负例/缺证；报告可点回固定源码和证据。
- **G4：证明增益再扩展（D-08）。** 单仓标签对照通过后，扩第二类 Profile 和双服务夹具；测效果、重复扫描成本和资源上限，再决定增量构建或分布式执行。

依赖顺序是 G0 → G1 → G2 → G3 → G4。每阶段更新这三份文档与实际状态，不新增平行路线图。
G0 须核实 Java `none/autobuild/manual` 的目标适用性；无构建不等于不需要依赖工具或执行隔离。
任务中断、租约过期、工件写完但发布失败等恢复验收在 G1 完成，不能留到最后才补。
首版仅实现 SQLi 专项切片；其他模式在界面标为未实现，不展示可运行的空壳选项。
独立任务组件可以在 G0 核验期间并行开发，但不能据此把 G0/G1 标为通过。

## 4. 端到端演示应看到什么
1. 在资产管理界面提交仓库链接；后台自动拉取、解析/构建/建库/提取，界面可追踪进度。
2. 准备完成后发布 READY 版本；资产详情可查接口、数据流、Guard、索引/程序库与质量说明。
3. 转到独立扫描工作台，从 READY 资产选项目/版本，选 Plan/Profile 和预算，点击运行才生成扫描任务。
4. Source-first 找路径；Sink-first 对未覆盖 Sink 做反查；规则补候选；结果汇入 Case。
5. Agent 在 Case 内查证，例如补查参数绑定/白名单/调用前提，并保存引用。
6. Verifier 保留真实问题，排除有有效保护的负例，把缺失前提项标待确认。
7. 报告回溯到资产、路径、工具/模型版本和原始工件；最后对照靶场标签。

## 5. 验收矩阵

| 检查 | 要证明的事 |
|---|---|
| 双界面与任务分离 | 资产纳入自动准备；准备完成不启动扫描；人工运行才新建 ScanRun |
| 就绪过滤与复用 | PARTIAL/FAILED 不可直接选；READY 同版本可被多个扫描引用；取消扫描不删资产 |
| 资产更新 | 新版本准备不影响旧版本或在途扫描；成功后再发布 |
| 多仓版本 | 每仓独立 commit，汇总为集合快照；仓/模块/服务映射不是一对一假设 |
| 查询一致性 | 搜索和程序查询绑定同一版本，过期索引不得充当当前证据 |
| 服务关系 | 发现调用线索不等于证明跨服务污点；未知关系必须保留 |
| 无构建场景 | 能得到基础资产，不把项目构建失败等同不可分析 |
| 构建失败/工具缺失 | 必要步骤失败不发布 READY；缺能力的计划禁用并指向资产中心 |
| 资产一致性 | 多个分析器引用同一资产对象，Entry 和 Source 不混淆 |
| Guard 反例 | 看见注解/校验不直接认定安全，要检查当前路径适用性 |
| 正反向搜索 | 有各自的任务/证据/缺口记录，而不是两个别名调用同一结果 |
| Case 去重 | 保留多方法来源、不同路径、反证与未解析边 |
| Agent 边界 | 不修改人选 Plan；预算耗尽不伪造完成 |
| 独立复核 | 使用原始证据和独立上下文，包含负例与待确认项；裁决绑定 case_revision/evidence_digest，证据变化后失效 |
| 幂等提交 | 同键同 payload 复用；同键不同 payload 冲突；并发只生成一个资源 |
| 发布 fencing | 过期 attempt 不得改步骤/绑定工件/发布，取消后不能迟到提交 |
| 执行与覆盖 | 预算耗尽/局部失败保留缺口；报告可用不等于覆盖完整；复核失败保留未复核 |
| 构建隔离 | 隔离器缺失时阻塞构建，不在宿主执行第三方脚本 |
| 可重放性 | 绑定 commit、资产快照、Plan/Profile、查询、模型与提示版本 |
| 效果对照 | 标签不进入模型上下文；限定类别、分母和去重规则，报告源码提示造成的偏差 |
